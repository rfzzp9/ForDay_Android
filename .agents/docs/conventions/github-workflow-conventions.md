# GitHub Workflow Conventions

## 목적

이슈 생성, 이슈 브랜치 생성, PR 작성, PR 업데이트 같은 GitHub 쓰기 작업의 기준을 정의한다.

커밋과 마찬가지로 GitHub 쓰기 작업은 사용자가 명시적으로 요청했을 때만 수행한다.

## 자동 실행 금지

다음 요청만으로는 이슈, 브랜치, PR을 생성하지 않는다.

- "작업해줘"
- "수정해줘"
- "검토해줘"
- "정리해줘"
- "PR 준비해줘"
- "이슈로 만들 수 있을지 봐줘"

이 경우에는 필요한 변경, 초안, 체크리스트, 권장 다음 단계를 제안할 수 있지만 실제 GitHub 쓰기 작업은 하지 않는다.

## 명시 요청 예시

다음처럼 사용자가 GitHub 작업을 직접 요청한 경우에만 실행한다.

- "이슈 생성해줘"
- "이 내용으로 GitHub 이슈 만들어줘"
- "이슈 브랜치 만들어줘"
- "123번 이슈 브랜치 생성해줘"
- "PR 작성해줘"
- "푸시하고 PR 열어줘"
- "draft PR 만들어줘"
- "이 PR 본문 업데이트해줘"

요청이 명확하지 않으면 실행 전에 확인한다.

## 이슈 생성 기준

이슈는 다음 정보가 충분할 때 생성한다.

- 문제 또는 목표
- 사용자 영향 또는 개발 목적
- 작업 범위
- 완료 조건
- 관련 파일, 화면, API, 로그 중 확인 가능한 단서

정보가 부족하면 먼저 이슈 초안을 작성하고 사용자에게 확인한다.

## 이슈 본문 기본 구조

```md
## 배경

## 작업 범위

## 완료 조건

## 참고
```

버그 이슈는 필요하면 다음 구조를 사용한다.

```md
## 증상

## 재현 방법

## 기대 동작

## 실제 동작

## 확인 범위
```

## 브랜치 생성 기준

브랜치는 사용자가 명시적으로 요청했거나, 이슈 작업 시작을 명시적으로 지시한 경우에만 생성한다.

브랜치 생성 전 확인한다.

- 현재 브랜치
- 작업 기준 브랜치
- 연결할 이슈 번호
- 현재 변경사항 존재 여부
- 기존 변경사항이 브랜치 이동에 영향을 주는지

현재 변경사항이 있으면 사용자 변경인지, 내가 만든 변경인지 구분한다. 브랜치 전환이나 생성이 위험하면 먼저 확인한다.

## 브랜치 네이밍

브랜치명에는 AI 도구 이름을 넣지 않는다.

금지 예시:

- `codex/123-login-fix`
- `claude/123-login-fix`
- `gemini/123-login-fix`
- `ai/123-login-fix`

권장 형식:

- `{type}/{issue-number}-{short-topic}`
- `{type}/{short-topic}`

권장 type:

- `feature`: 기능 추가
- `fix`: 버그 수정
- `refactor`: 동작 변화 없는 구조 개선
- `docs`: 문서 변경
- `test`: 테스트 추가 또는 수정
- `chore`: 설정, 빌드, 의존성, 운영성 변경

예시:

- `feature/123-signup-flow`
- `fix/123-token-refresh`
- `refactor/home-state-holder`
- `docs/agent-workflow-conventions`
- `test/login-viewmodel`
- `chore/android-gradle-update`

브랜치명 규칙:

- 소문자 kebab-case를 사용한다.
- 한글, 공백, 밑줄, 특수문자는 사용하지 않는다.
- 이슈가 있으면 가능한 한 이슈 번호를 포함한다.
- 제목보다 작업 범위를 짧게 표현한다.
- 타입이 애매하면 변경의 주 목적을 기준으로 고른다.

## PR 생성 기준

PR은 사용자가 명시적으로 요청했을 때만 생성한다.

PR 생성 전 확인한다.

- 현재 브랜치가 작업 브랜치인지
- base branch가 맞는지
- 커밋되지 않은 변경사항이 없는지
- 필요한 커밋이 모두 포함됐는지
- 불필요한 파일, local 파일, secret 파일, generated 파일이 포함되지 않았는지
- 가능한 검증을 수행했는지
- 검증하지 못한 항목이 있으면 이유가 정리됐는지

## PR 제목

PR 제목은 변경의 목적을 드러내는 짧은 문장으로 작성한다.

권장 형식:

- `[type] summary`
- `summary`

예시:

- `[fix] 로그인 토큰 갱신 실패 처리`
- `[docs] 에이전트 문서 운영 기준 정리`
- `홈 화면 상태 처리 개선`

저장소에 별도 규칙이 있으면 그 규칙을 우선한다.

## PR 본문 기본 구조

```md
## Summary

## Changes

## Verification

## Notes
```

한글 본문이 자연스러운 저장소에서는 다음 구조를 사용한다.

```md
## 요약

## 변경사항

## 검증

## 참고
```

검증하지 못한 항목은 숨기지 않고 `검증하지 못함`으로 적는다.

## Draft PR 기준

다음 중 하나라도 해당하면 draft PR을 우선한다.

- 구현은 진행 중이지만 방향 공유가 필요한 경우
- 테스트나 빌드 검증이 끝나지 않은 경우
- 사용자 확인이 필요한 설계 선택이 남은 경우
- 리뷰 전에 후속 커밋이 예정된 경우

사용자가 ready PR을 명시하면 ready PR로 생성한다.

## PR 업데이트 기준

PR 제목, 본문, reviewer, label, base branch, draft 상태 변경도 GitHub 쓰기 작업이다.

사용자가 명시적으로 요청했을 때만 변경한다.

## 커밋 규칙과의 관계

커밋은 `.agents/docs/conventions/commit-conventions.md`를 따른다.

PR 생성 전에 커밋이 필요하면 사용자에게 커밋 요청이 있었는지 확인한다. 사용자가 PR 생성을 명시했고 커밋이 필요한 상태라면, 어떤 파일을 어떤 커밋으로 묶을지 먼저 정리한 뒤 진행한다.

## 최종 응답

GitHub 쓰기 작업을 수행한 경우 최종 응답에는 다음을 포함한다.

- 생성 또는 수정한 이슈, 브랜치, PR
- base branch와 head branch
- 포함한 커밋
- 검증 결과
- 남은 확인 사항

GitHub 쓰기 작업을 하지 않은 경우에는 하지 않은 이유를 짧게 말한다.
